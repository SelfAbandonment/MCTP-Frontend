# 协作规范（MCTP-Frontend）

分支与发布规则与后端仓库保持一致；后端文档 `MCTP-API/docs/showdoc/开发规范/Git 工作流.md` 是完整版，这里只列前端要点。

## 分支

- `main`：生产分支，只接收 release PR 与 hotfix 回流，合并后打 tag
- `develop`：集成分支，**禁止直接推送**，功能分支走 PR
- 功能分支：`feat/`、`fix/`、`docs/`、`refactor/`、`test/`、`chore/`，从最新 `develop` 切出
- 合并统一 **Squash merge**，PR 标题即最终 commit message

## 提交

遵循 Conventional Commits：`feat:`、`fix:`、`docs:`、`refactor:`、`test:`、`chore:`。

## PR 要求

- 填完 PR 模板：改了什么、关联 issue、影响面、验证证据、回滚方式
- 必需检查：`lint`、`test`、`build`
- 本地等价：`npm run lint:check`、`npm test`、`npm run build`

## 发布

1. `develop` 通过检查后开 release PR：`develop → main`，标题 `release: vX.Y.Z`
2. 合并后打 tag：`git tag -a vX.Y.Z -m "vX.Y.Z" && git push origin vX.Y.Z`
3. `deploy.yml` 在 push `main` 后构建并发布 GitHub Pages
4. 发布后把 `package.json` 的 `version` 推进到下一个开发版本

## CI / Jenkins 分工

| 位置 | 触发 | 负责 |
|---|---|---|
| Actions `ci.yml` | PR、push 到 `main`/`develop` | `lint`（ESLint）、`test`（单测 + 覆盖率门禁）、`build`（上传 dist）、`preview`（复用 dist 部署 PR 预览） |
| Actions `deploy.yml` | push `main`、手动 | 校验 API 变量、测试、构建、发布 Pages |
| Jenkins（Multibranch） | PR、`develop`、`main` | 同口径复核 + Lighthouse 性能/无障碍门禁 |

Jenkins 的 Lighthouse 门禁会卡 CLS 与无障碍；构建产物归档在 `.lighthouseci/`。
